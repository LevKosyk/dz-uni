# GraphQL
GraphQL - це предметно-орієнтована мова запитів, яка використовується для роботи з API. Вона дозволяє клієнту точно вказувати, які дані необхідно отримати від сервера, а також у якій структурі вони мають бути повернуті.

GraphQL був створений у Facebook для спрощення взаємодії між клієнтськими застосунками та серверною частиною. Пізніше він став відкритою технологією та почав широко використовуватися в web- та mobile-розробці.

Головна особливість GraphQL полягає в тому, що клієнт сам формує структуру запиту. Наприклад, якщо frontend-застосунку потрібне тільки ім’я користувача та його електронна пошта, немає необхідності отримувати весь об’єкт користувача з десятками інших полів.

GraphQL часто використовується як альтернатива REST API. При цьому GraphQL не є повноцінною мовою програмування. За допомогою нього не можна реалізувати весь backend, написати бізнес-логіку або створити сервер. Його основна задача - описувати, які дані клієнт хоче отримати або змінити через API.


## 1. Яку задачу розв’язує GraphQL і хто її кінцевий користувач

Основна задача GraphQL - організувати зручну взаємодію між клієнтом і сервером.

У сучасному застосунку часто існує backend, який зберігає та обробляє дані, і frontend, який показує ці дані користувачу. Frontend повинен якось звертатися до backend та отримувати необхідну інформацію.

Наприклад, у застосунку соціальної мережі можуть бути такі дані:

- користувачі;
- публікації;
- коментарі;
- друзі;
- повідомлення;
- фотографії.

Frontend може потребувати різні набори даних для різних сторінок.

Наприклад, на сторінці профілю потрібні:

- ім’я користувача;
- фотографія;
- опис профілю.

На сторінці налаштувань можуть бути потрібні:

- email;
- номер телефону;
- мова інтерфейсу.

GraphQL дозволяє кожній сторінці зробити свій запит і отримати тільки ті дані, які реально потрібні.

Приклад:

```graphql id="graph1"
query {
  user(id: 1) {
    name
    email
  }
}
```

У цьому випадку сервер поверне тільки `name` та `email`.

Це дозволяє зменшити кількість зайвих даних, які передаються між сервером і клієнтом.

### Проблема зайвих даних

У REST API сервер часто має готовий endpoint, наприклад:

```text
GET /users/1
```

Він може повертати:

```json id="json1"
{
  "id": 1,
  "name": "Lev",
  "email": "lev@example.com",
  "phone": "+380...",
  "address": "Kharkiv",
  "birthDate": "2000-01-01",
  "createdAt": "...",
  "updatedAt": "..."
}
```

Але якщо клієнту потрібне тільки ім’я, всі інші дані будуть зайвими.

Цю проблему часто називають **over-fetching**, GraphQL дозволяє цього уникнути.
### Проблема недостатньої кількості даних

Існує також протилежна проблема - **under-fetching**.

Наприклад, якщо через REST потрібно отримати користувача та його публікації, можуть знадобитися два запити:

```text
GET /users/1
GET /users/1/posts
```

У GraphQL це можна зробити одним запитом:

```graphql id="graph3"
query {
  user(id: 1) {
    name
    posts {
      title
    }
  }
}
```

### Хто є кінцевим користувачем GraphQL

GraphQL призначений насамперед для програмістів.

Його використовують:

- frontend-розробники;
- backend-розробники;
- mobile-розробники;
- full-stack розробники.



## 2.  Робочий приклад коду

Розглянемо найпростіший GraphQL-запит.

```graphql id="graph4"
query {
  user(id: 1) {
    name
    email
  }
}
```

У цьому прикладі:

`query` означає, що ми хочемо отримати дані.

`user` — поле або запит, який повертає користувача.

`id: 1` — аргумент, який вказує, якого саме користувача потрібно знайти.

Усередині фігурних дужок:

```graphql id="graph5"
{
  name
  email
}
```

ми вказуємо поля, які хочемо отримати.

Сервер може повернути таку відповідь:

```json id="json2"
{
  "data": {
    "user": {
      "name": "Lev",
      "email": "lev@example.com"
    }
  }
}
```

Важливо, що структура відповіді дуже схожа на структуру запиту.

Якщо ми додамо нове поле:

```graphql id="graph6"
query {
  user(id: 1) {
    name
    email
    phone
  }
}
```

то у відповіді з’явиться `phone`.

```json id="json3"
{
  "data": {
    "user": {
      "name": "Lev",
      "email": "lev@example.com",
      "phone": "+380..."
    }
  }
}
```

### GraphQL-схема

Для роботи GraphQL сервер повинен мати схему.

Наприклад:

```graphql id="graph7"
type User {
  id: ID!
  name: String!
  email: String!
}

type Query {
  user(id: ID!): User
}
```

Тут описується тип `User`.

Він має три поля:

```graphql id="graph8"
id: ID!
name: String!
email: String!
```

Символ `!` означає, що поле є обов’язковим і не повинно мати значення `null`.

Далі описується запит:

```graphql id="graph9"
user(id: ID!): User
```

Він приймає `id` і повертає об’єкт типу `User`.

Отже, GraphQL-схема визначає правила, за якими клієнт може працювати з API.

## 3. Основні операції GraphQL

GraphQL має декілька основних типів операцій.

### Query

`Query` використовується для отримання даних.

Приклад:

```graphql id="graph10"
query {
  users {
    id
    name
  }
}
```

Цей запит отримує список користувачів.

### Mutation

`Mutation` використовується для зміни даних.

Наприклад, можна створити нового користувача:

```graphql id="graph11"
mutation {
  createUser(name: "Lev", email: "example@exam.com") {
    id
    name
  }
}
```

Після створення сервер може повернути:

```json id="json4"
{
  "data": {
    "createUser": {
      "id": 10,
      "name": "123@gmail.com"
    }
  }
}
```

Mutation також може використовуватися для:

- створення об’єктів;
- оновлення даних;
- видалення даних.

### Subscription

У GraphQL також існують `subscription`.

Вони використовуються для отримання оновлень у реальному часі.

Наприклад:

```graphql id="graph12"
subscription {
  newMessage {
    id
    text
  }
}
```

Коли з’являється нове повідомлення, сервер може автоматично відправити його клієнту.

Це може використовуватися у:

- чатах;
- системах повідомлень;
- live dashboards;
- онлайн-іграх.

## 4. Вдале та невдале рішення у синтаксисі GraphQL

Однією з переваг GraphQL є можливість запитувати тільки необхідні поля. Але цю можливість також можна використовувати неправильно.

### Вдале рішення

Припустимо, на сторінці потрібно показати тільки ім’я користувача та його email.

Хороший GraphQL-запит буде таким:

```graphql id="graph13"
query {
  user(id: 1) {
    name
    email
  }
}
```

Це вдале рішення, тому що запит:

- простий;
- легко читається;
- містить тільки необхідні поля;
- не створює зайвого навантаження;
- не передає непотрібні дані.

Такий підхід добре показує основну ідею GraphQL - клієнт отримує саме те, що йому потрібно.

### Невдале рішення

Можна написати й такий запит:

```graphql id="graph14"
query {
  user(id: 1) {
    id
    name
    email
    phone
    address
    birthDate
    createdAt
    updatedAt
    posts {
      id
      title
      text
      comments {
        id
        text
        author {
          id
          name
          email
        }
      }
    }
  }
}
```

Сам синтаксис цього запиту правильний.

Але якщо на сторінці потрібно показати тільки `name` та `email`, це невдале рішення.

Причина полягає в тому, що клієнт запитує велику кількість непотрібних даних.

Крім того, вкладені запити можуть бути достатньо складними.

Наприклад:

```graphql id="graph15"
posts {
  comments {
    author {
      ...
    }
  }
}
```

Серверу може знадобитися виконати багато операцій або запитів до бази даних.

Тому навіть у GraphQL потрібно правильно обирати дані, які необхідно отримати.

### Інший невдалий приклад

Ще одним поганим рішенням може бути створення дуже великого запиту, який намагається отримати майже всі дані програми за один раз.

Наприклад:

```graphql id="graph16"
query {
  users {
    posts {
      comments {
        author {
          posts {
            comments {
              text
            }
          }
        }
      }
    }
  }
}
```

Такий запит може бути складним для сервера та бази даних.

Отже, GraphQL дає багато гнучкості, але розробник повинен використовувати її правильно.


## 5. Чому без GraphQL у деяких випадках було б гірше

Без GraphQL клієнт має сильніше залежати від структури API, яку створив backend.

Наприклад, frontend-розробнику можуть знадобитися нові дані.

У REST може виникнути необхідність:

1. змінити існуючий endpoint;
2. створити новий endpoint;
3. попросити backend-розробника додати потрібне поле;
4. змінити формат відповіді.

У GraphQL, якщо необхідне поле вже існує в схемі, frontend може просто додати його до свого запиту.

Наприклад:

Спочатку:

```graphql id="graph19"
query {
  user(id: 1) {
    name
  }
}
```

Пізніше frontend також потребує email:

```graphql id="graph20"
query {
  user(id: 1) {
    name
    email
  }
}
```

Backend API при цьому не потрібно змінювати.

Ще одна перевага GraphQL - сильна типізація.

Схема одразу описує, які дані можна отримати.

Наприклад:

```graphql id="graph21"
type User {
  id: ID!
  name: String!
  email: String!
}
```

Розробник бачить, що `User` має конкретні поля та конкретні типи.

Це спрощує:

- розробку;
- документацію;
- перевірку запитів;
- роботу frontend та backend команд.



## Висновок

GraphQL - це предметна мова запитів, створена для роботи з API. Її головне завдання полягає в тому, щоб зробити отримання та зміну даних між клієнтом і сервером більш гнучкими.

Головною перевагою GraphQL є можливість клієнта самому визначати, які саме дані він хоче отримати. Це допомагає зменшувати кількість зайвих даних та у багатьох випадках скорочувати кількість запитів до сервера.

GraphQL також має систему типів, підтримує `query`, `mutation` та `subscription`, що дозволяє використовувати його для читання, зміни та отримання даних у реальному часі.

Без GraphQL аналогічні задачі зазвичай вирішувалися б за допомогою REST API. REST залишається хорошим і простим рішенням для багатьох систем, але в складних застосунках GraphQL може бути зручнішим, оскільки дозволяє клієнту більш точно керувати отриманими даними.

При цьому GraphQL також має свої недоліки. Складні вкладені запити можуть створювати значне навантаження на сервер, а реалізація GraphQL API потребує додаткової конфігурації.

Отже, GraphQL є хорошим прикладом предметної мови: він не намагається замінити звичайні мови програмування, а вирішує одну конкретну задачу — зручну та гнучку роботу з API.
